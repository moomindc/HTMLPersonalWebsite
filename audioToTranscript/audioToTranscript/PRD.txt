PRD: Local-Only AI Audio Transcription Web Application
1. Product Overview
Build a fully local web application that allows a user to upload an audio file, transcribe the speech to text using a locally executed AI model, and copy the resulting transcript to the clipboard.
The application must operate 100% locally on the user’s machine after loading the web app, with no server-side transcription and no requirement to upload audio data to any remote service. The app should support downloading transcription models dynamically, caching them locally so they do not need to be downloaded again on future page loads.
The UI should be simple, fast, and accessible, with an optional expandable Options panel containing configurable transcription settings. User-selected transcription settings should persist using cookies.

2. Goals
Primary Goals

Allow a user to upload an audio file in common formats (at minimum MP3, with flexibility for WAV, M4A, OGG, FLAC, etc.).
Run speech-to-text locally in the browser using a selectable AI model.
Display the transcription result in a text output area.
Provide a “Copy to Clipboard” button once transcription is complete.
Allow users to configure transcription options via an expandable Options panel.
Allow users to select from multiple transcription models.
Dynamically download models on demand.
Cache downloaded models locally so they do not need to be redownloaded on page refresh/reopen.
Save user-selected transcription settings in a cookie.

Secondary Goals

Provide clear progress and status indicators for:

model download
model load
transcription progress


Handle unsupported files and transcription failures gracefully.
Work reasonably well on modern desktop browsers.


3. Non-Goals
The initial version does not need to include:

cloud-based transcription
user accounts or authentication
storage of uploaded audio files beyond runtime use
collaborative features
speaker diarization (unless supported later)
translation to other languages (unless explicitly enabled later)
punctuation/editorial rewriting beyond what the model already provides
exporting to advanced formats like DOCX/PDF/SRT/VTT in v1
batch processing multiple files in v1


4. Target Users
Primary User
A user who wants a private, local, browser-based transcription tool for audio files without sending data to the cloud.
User Needs

privacy
simplicity
control over model choice
local persistence of settings
no repeated downloads of models
easy ability to copy transcript text


5. User Stories

As a user, I want to upload an audio file so I can transcribe spoken content.
As a user, I want the app to support common audio file formats so I am not restricted to MP3 only.
As a user, I want to choose which transcription model to use so I can balance speed and accuracy.
As a user, I want the selected model to download automatically if it is not already available locally.
As a user, I want downloaded models cached locally so I do not have to redownload them every time I open the app.
As a user, I want to configure transcription options in an expandable panel so the main UI remains clean.
As a user, I want my selected options remembered in a cookie so I do not need to set them every time.
As a user, I want to see progress/status while the model is downloading or transcription is running.
As a user, I want to read the generated transcript in a large text area.
As a user, I want a one-click Copy to Clipboard button after transcription completes.
As a user, I want clear error messages if the file is unsupported or the transcription fails.

6.2 Local-Only Transcription
The application must:

perform transcription fully on the client side
avoid uploading user audio to any server for processing
run AI inference using a browser-compatible local model approach (e.g., WebAssembly/WebGPU/Web Worker-backed local inference)

Implementation (as built):
Uses Transformers.js v3 (@huggingface/transformers@3) loaded from CDN (jsDelivr) inside a Web Worker.
Inference device resolution:
  - Attempts WebGPU first — checks for shader-f16 feature support.
  - Falls back to WASM (CPU) if WebGPU is unavailable or fails.
  - WebGPU load has a 45-second timeout; if exceeded, automatically retries on WASM.
The worker reports the active device ('webgpu' | 'wasm') to the main thread on model_ready.
The main thread status area displays "Ready — GPU", "Ready — CPU (N cores)", or "Ready" accordingly.

Acceptance Criteria

No audio content is sent to a remote backend for transcription.
App remains functional after initial load without server-side inference dependencies.

8.3 Local Inference Considerations
Implementation may use a client-side inference approach such as:

WebAssembly-based speech model runtime
WebGPU acceleration when available
Web Workers to avoid blocking the main UI thread

The architecture should prefer:

non-blocking inference
responsive UI during long-running operations
progress updates to main thread

Implementation (as built):
Library:     Transformers.js v3 (@huggingface/transformers@3) via CDN (jsDelivr).
             No build step required — loaded via import in worker.js (ES module Worker).
Model type:  automatic-speech-recognition pipeline (Whisper ONNX models from Hugging Face Hub).
Device:      WebGPU (fp16) preferred; WASM (CPU) fallback.
             WebGPU load has 45-second timeout before automatic WASM retry.
Threading:   All inference runs in a dedicated Web Worker (worker.js) to keep the UI thread unblocked.
Chunking:    Audio processed in 30-second chunks with 5-second stride for long-file support.
             A chunk_callback fires per completed chunk to report transcription progress (0–0.99).
             A callback_function fires every token for liveness confirmation during slow first chunks.
             An interval heartbeat (every 5 s) logs a warning if the pipeline appears stalled.
Timestamps:  Supported via return_timestamps: 'word' when the timestamps option is enabled.
Language/task: Only passed to the pipeline for multilingual models; suppressed for English-only models.

8.4 Audio Decoding
The app should use browser-supported APIs or compatible decoding libraries to normalize input audio as needed for the transcription model.

Implementation (as built):
Uses the browser's built-in Web Audio API (AudioContext.decodeAudioData).
No external audio library required.
Steps:
  1. Read file as ArrayBuffer (FileReader).
  2. Decode compressed audio to PCM via AudioContext.decodeAudioData.
  3. Mix down to mono by averaging all channels.
  4. Resample to 16 kHz (Whisper's required sample rate) using OfflineAudioContext if needed.
Decoding runs on the main thread (fast enough for typical files); the audio buffer is then
transferred (zero-copy) to the Web Worker via postMessage transferable.

9. Architecture (as built)
9.1 Module Breakdown

File                 | Responsibility
---------------------|---------------------------------------------------------------
index.html           | App shell — semantic HTML structure, no inline logic
css/app.css          | All visual styles
js/app.js            | Entry point: state machine, event wiring, single render() pass
js/modelRegistry.js  | Static model catalogue — single source of truth for model metadata
js/modelManager.js   | Cache probe (Cache API) + Worker interface for model load/ready
js/settings.js       | Cookie read/write (atSettings cookie, 365-day expiry)
js/audioProcessor.js | File validation, Web Audio decode, mono mix, 16 kHz resample
js/clipboardManager.js | Clipboard API copy with textarea fallback
js/worker.js         | Web Worker: Transformers.js pipeline, device resolution, inference

app.js maintains a single `state` object and a single `render()` function.
No framework is used. All DOM writes are funnelled through render().

9.2 Web Worker Message Protocol

Main → Worker:
  { type: 'load_model',  modelId: string,        options: { preferWebGPU: true } }
  { type: 'transcribe',  audio: Float32Array,     options: { language, task, timestamps, cleanupWhitespace } }

Worker → Main:
  { type: 'model_loading' }
  { type: 'download_progress', file: string, progress: number }   // 0..1
  { type: 'model_ready',       modelId: string, device: 'webgpu'|'wasm' }
  { type: 'transcribing' }
  { type: 'transcription_progress', progress: number }            // 0..0.99
  { type: 'result',  text: string, chunks: array|null }
  { type: 'error',   message: string }

9.3 Storage Strategy

Cookies (atSettings):  user preferences only — lightweight JSON, 365-day expiry
Cache API:             model ONNX files cached automatically by Transformers.js
                       (env.useBrowserCache = true)
In-memory state:       selected file, transcript text, runtime status, download progress

11. Primary User Flow

User opens the app.
App loads saved settings from cookie.
App checks which models are already cached locally.
User uploads an audio file.
User optionally changes model and/or settings in the Options panel.
If selected model is not cached, app downloads it and shows progress.
User clicks Transcribe.
App runs local transcription and shows status/progress.
Transcript appears in output panel.
Copy to Clipboard button becomes enabled.
User copies transcript text.

13. Performance Requirements

UI should remain responsive during model download and transcription.
Heavy computation should not freeze the page.
Cached models should load faster than first-time download.
App should provide visible progress/status for long operations exceeding ~1 second.


14. Privacy & Security Requirements

Audio files must remain local to the user’s machine during transcription.
No transcript or audio should be transmitted to a server for processing.
Cookies should store only lightweight preferences, not sensitive content or large data.
App should clearly communicate that transcription occurs locally.

16. Implementation Notes
16.1 Build and Dependencies
No build step or package manager required.
The app runs directly as static files in any modern browser.
Single external dependency: Transformers.js v3 loaded from CDN in worker.js:
  import { pipeline, env } from
    'https://cdn.jsdelivr.net/npm/@huggingface/transformers@3/dist/transformers.min.js';
All other modules are plain ES modules loaded via <script type="module" src="./js/app.js">.

16.2 Running Locally
Open index.html in a modern browser. A local HTTP server is recommended (e.g. VS Code Live Server,
python -m http.server) to avoid CORS restrictions on module imports from the filesystem.
Web Worker requires a non-file:// origin to load ES module workers in Chrome.

16.3 Key Decisions and Rationale
Decision                         | Rationale
---------------------------------|--------------------------------------------------
Transformers.js v3 via CDN       | No build step; Whisper ONNX models from HF Hub
WebGPU → WASM fallback           | GPU acceleration where available; always works otherwise
45s WebGPU timeout               | Prevents silent hangs on GPU driver stalls
Audio decoded on main thread     | Web Audio API not available in Workers; fast enough for typical files
Audio transferred to Worker      | Zero-copy postMessage with transferable ArrayBuffer
30s/5s chunk stride              | Handles large audio without OOM; matches Transformers.js defaults
Chunk + token callbacks          | Provides granular progress and liveness signals
Model IDs = HF repo paths        | Passed directly to pipeline(); no mapping layer needed
Cookie (not localStorage)        | Works across origins; easy to inspect; small payload
Cache API for models             | Written automatically by Transformers.js (env.useBrowserCache)
Single render() function         | Predictable, debuggable state → DOM updates
